# Versioned documentation releases

`dev` follows the reviewed development commit in `code-version.json`. `versions.json`
contains every formal `vMAJOR.MINOR.PATCH` release and selects the newest one
as `stable`. The website root opens stable.

Each release records a full `code_sha` and `docs_sha`. Its Markdown pages,
public figures, figure sources and API mapping are extracted from that frozen
documentation commit. API fragments are generated by the exporter in the
selected code commit. The current website theme renders all versions and
provides an updated version menu. Release pages show their code and document
commits and omit the edit-current-page action.

## Prepare a release

1. Choose a reviewed main commit whose `Project.toml` version matches the tag.
2. Prepare and review the release page content. Commit that content snapshot
   on the documentation history before adding its SHA to `versions.json`.
3. Append the new version with its code and documentation SHAs. Preserve the
   older entries. Select the newest formal version as stable. Update the dev
   pin to the reviewed development commit when appropriate.
4. Prepare exact, clean code checkouts. When one code commit supplies every
   version, set `DOCS_CODE_PATH` to that checkout. Otherwise set `DOCS_CODE_ROOT`
   to a directory with one checkout per SHA, named by its full SHA.
5. Run the candidate build and review all version entries, source links,
   examples, math, figures and themes.

```bash
npm ci --prefix docs
export DOCS_CODE_PATH=/absolute/path/to/clean-code-checkout
export DOCS_CHECK_EXAMPLES=1
npm run docs:build-site --prefix docs -- --preview
npm run docs:preview --prefix docs
```

The candidate badge remains visible even though the code checkout is clean.
`version.json` in every output directory and the root `versions.json` record
the identities and candidate status. A failed build retains the previous
complete artifact.

## Publish after approval

The first release uses code `425f7df50decd64fbba16180e0c96970894dabfb` and tag
`v0.1.0`. The exact candidate documentation snapshot is listed in
`versions.json`. The content snapshot must be an ancestor of the final docs
commit so a normal push includes its Git objects.

After the candidate code and documentation checks pass, create the code tag
at the approved code SHA and publish its GitHub Release. Merge the reviewed
documentation changes into `docs`. Its push workflow builds and deploys the
complete website. A later rebuild can be dispatched manually using the
Documentation workflow on the `docs` ref.

The formal workflow verifies that every configured tag resolves to its code
SHA, each package version matches its tag, and each GitHub Release is
published with `draft=false` and `prerelease=false`. The builder requires all
formal tags to remain configured. The deployment check validates dev, stable,
every release, their code links, figures and published version index. It
rejects candidate artifacts. A Release or tag alone does not trigger this
docs-branch workflow. Publication is deliberately completed through the
reviewed docs update or manual dispatch.

The first release does not require a numerical code change. Its documentation
tooling comes from the existing main code commit. The VitePress dependency
versions and lockfile remain the build environment for the website.
